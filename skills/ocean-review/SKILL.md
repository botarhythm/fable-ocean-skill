# Ocean Review — 実装前・異種AI 2巡レビューの型（`/ocean-review`）

Ocean 型は Fable（設計）× Opus/Sonnet（実装）を文書ハンドオフで繋ぐ。**ocean-review はその手前に「別系統のモデル（Codex CLI = GPT 系）による敵対的レビュー」を1枚差し込む**拡張。同じ設計を同じ系統のモデルで見直しても盲点は残る——**異種の推論系**にコードと設計を生で読ませ、2巡させることで、実装前に設計の穴（事故・矛盾・スコープ漏れ）を潰す。

- **Ocean 本体との関係**: これは Ocean §5（検証ループ）と §1（レビュー発注）の**実装前フェーズ**。Ocean §9 の「監査・診断の一次情報は要約せず生で渡す」を異種AIレビューに適用したもの（Codex に対象コードを read-only で直読させる＝要約越しにしない）。
- **なぜ2巡か**: 1巡目=指摘（Critical/High/Medium/Low）。あなたが咀嚼して採否と対案を作る。2巡目=採否を突き返して**裁定**（総合 GO/条件付きGO）を取る。1巡だけだと「指摘の言いっぱなし」で終わり、対案の妥当性と見落としが検証されない。**採否を相手にぶつけ返す往復**が品質の実体。

## 前提（プロジェクトのCLAUDE.mdが優先）

- Codex CLI が導入済み（`codex --version` で確認）。未導入ならユーザーに提示して止まる。
- **モデルは5.6系**（例: `gpt-5.6-sol`）。プロジェクトによって指定が違えばそのCLAUDE.md/メモが優先。
- レビュー記録の置き場は対象プロジェクトの `docs/reviews/`（Ocean §6 の永続化規約。scratchpad に置かない）。
- このコマンドは**レビューと採択の記録まで**。実装の着手・コミット・デプロイは Ocean 本体の承認ゲート（§7）に従う。

## 0. 対象を用意する

レビュー対象は「異種AIが読んで穴を指摘できる粒度」であること:

- **設計メモ / 実装計画**（推奨）— ファイル1枚（`docs/design-*.md` 等）にゴール・確定事項・スコープ・未決点を書き切る。
- **既存コードの差分 / PR** — 対象ファイル群を read-only で読ませる。
- 対象が曖昧で1枚に落とせないなら、先に Ocean §8（壁打ち）でブリーフ化してから来る。

**渡し方の原則（Ocean §9）**: 判断の根拠になる一次情報（設計本文・対象コード・前回レビュー記録・AC）は**要約せず、Codex に read-only sandbox で直読させる**。プロンプトにはパスと観点だけ書き、中身はファイルで読ませる。

## 1. 第1ターン（指摘を受ける）

対象プロジェクトのディレクトリに `cd` してから実行する（**trusted directory 判定と相対パス解決のため**）:

```bash
cd <対象repo> && codex exec -m <5.6系モデル> --sandbox read-only --skip-git-repo-check "<レビュー依頼プロンプト>"
```

- `--sandbox read-only` — Codex に**コードを読ませるが書かせない**。一次情報を生で渡す経路。
- `--skip-git-repo-check` — repo 直下でない/信頼設定が無い環境での「Not inside a trusted directory」エラーを回避（下の「落とし穴」参照）。
- 数分かかる。`tail -150` 等で末尾（総括と指摘一覧）を確実に取る。

### レビュー依頼プロンプトの型

```
あなたはシニアレビュアー。<新規実装/既存改修>の<設計メモ/差分>をレビューしてください。

対象: <設計本文の相対パス>（必読）
背景資料（必要に応じて読む・相対パス）:
- <ADR/決定記録>
- <前回レビュー記録>
- <AC＝受入条件のタスク文書>
- <流用元/関連実装の実物>

前提（変更不可の確定事項・レビュー対象外）:
- <店主決定済みで議論しない事項を列挙。ここを書かないと決定済みの点を蒸し返される>

レビュー観点:
1. 設計の欠陥・事故につながる穴（特に <このプロジェクト固有の赤線: 財務/公開/セキュリティ/レイテンシ等>）
2. 前回レビュー合意事項との矛盾
3. <未決点> への推奨
4. 流用元実装と設計メモの不整合

出力: 指摘を [Critical]/[High]/[Medium]/[Low] で番号付き列挙。各指摘に理由と具体的な修正案。最後に未決点への回答。日本語で。
```

**要点**: ①「前提（レビュー対象外）」を必ず書く——書かないと確定済みの決定を蒸し返されて往復が無駄になる。②「赤線」をプロジェクト固有で明示——汎用レビューより事故検出率が上がる。③重大度ラベルを強制——採否の優先順位付けに効く。

## 2. 咀嚼（あなたの仕事＝ここが最上位モデルの出番）

指摘を3つに仕分ける。**Ocean のモデル選択でいう「判断が成果物」の局面**なので、ここは薄いモデルに丸投げしない:

- **全面採用** — 妥当。設計にどう落とすかまで決める。
- **条件付き採用（対案あり）** — 指摘は正しいが、そのままの修正案はスコープ/コストが合わない。**対案を作り、2巡目で妥当性の裁定を求める**。
- **逆質問** — 指摘の全文が取れなかった（文字化け・欠落）、または前提が食い違っている点を問い返す。

仕分けの副産物として、**採用する指摘は先に設計本文へ反映**しておく（2巡目は「反映済みの採否リスト」を見せる形になり、裁定が速い）。

## 3. 第2ターン（採否を突き返し、裁定を取る）

**同じ Codex セッションを継続する**（第1ターンの文脈・サンドボックス設定を引き継ぐ）:

```bash
cd <対象repo> && codex exec resume --last "<採否提示プロンプト>"
```

### 採否提示プロンプトの型

```
咀嚼結果と採否です。異議・見落としがあれば指摘し、最後に総合判定（実装GO/条件付きGO）を出してください。

【全面採用】
- #N <指摘要旨>: <どう設計に反映したか>
...

【条件付き採用（対案あり・判定求む）】
- #N <指摘>: <対案>。これで<AC/赤線>を構造的に満たせるか判定を。
...

【逆質問】
- #N の全文が当方のキャプチャで欠落した。要点を再掲してほしい。当方の対案: <...>。妥当性の判定を。
```

2巡目の返しには**新規の追加指摘が出ることが多い**（対案が新たな穴を開けるため）。これも仕分けて設計に反映する。総合判定が「条件付きGO」なら、**列挙された必須条件を設計に落とし切ってから**実装GOとする。

## 4. 反映と記録（学びのループ）

- **採択は設計本文へ反映**。設計メモに「レビュー採択セクション（§N）」を設け、「§N は §1〜前節に優先」と明記——実装者（下位モデル/別AI）が確定仕様を1箇所で読める。
- **レビュー記録を `docs/reviews/<slug>-codex-review-YYYY-MM-DD.md` に残す**: レビュアー（Codex バージョン・モデル）／対象／第1ターン指摘の要点／第2ターン裁定／実装GOの必須条件／実機GO条件。金額・秘匿値は書かない（Ocean の財務赤線）。
- この記録は次回の同種レビューの「前回合意事項」になり、往復を減らす。**現場で踏んだ落とし穴は下の節に追記する**（型そのものを育てる）。

## 落とし穴（現場で困った事実・恒久反映）

1. **`codex exec` は trusted directory でないと即エラー**（`Not inside a trusted directory and --skip-git-repo-check was not specified`）。対象repo内に `cd` し `--skip-git-repo-check` を付ける。発注元repoから相対パスで対象を指すと動かない——**対象repo内で実行し、背景資料は相対パスで渡す**。
2. **`codex exec resume --last` は `--sandbox` フラグを受け付けない**（`error: unexpected argument '--sandbox'`）。2巡目はサンドボックス指定を書かない（第1ターンの設定を継承する）。
3. **出力キャプチャが文字化け/欠落することがある**（Windows コンソール cp932 等）。重要な指摘が読めなければ、セッションJSONL から回収できる: `~/.codex/sessions/YYYY/MM/DD/rollout-*.jsonl` の最新ファイルの `payload.type == "agent_message"` を拾う。**欠落した指摘は2巡目で「全文再掲」を逆質問**して確実に取る。
4. **「前提（レビュー対象外）」を省くと決定済み事項を蒸し返される**。店主が決めた器・モデル・方式は前提として固定して渡す。
5. **方針転換が起きたら差分レビューを1セッションで続ける**。`resume --last` で同じ Codex に「転換内容＋新設計」を渡すと、前段の文脈を保ったまま差分だけ見てくれる（新規セッションより往復が速い）。

## Ocean 本体との接続まとめ

| Ocean 本体 | ocean-review での対応 |
|---|---|
| §1 発注（レビュー） | 実装前レビューを異種AIで1枚差し込む |
| §5 検証ループ | 実装後の抜き取り監査に対し、**実装前**の敵対的検証を担う |
| §7 承認ゲート | レビューは止まらないが、GO後の実装/デプロイは本体のゲートに従う |
| §9 セッション経済学 | 一次情報（コード・設計）を要約せず Codex に生で読ませる／2巡は1セッション継続で立ち上げ費を払わない |
