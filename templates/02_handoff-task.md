# 02 ハンドオフ文書テンプレート

version: 1.4 (2026-07-02) / 制定: Fable-5

Fable-5 が発注し、Opus 4.8 / Sonnet 5 の**新規セッション**が単独で消費する仕様書。往復は 1 ファイルで完結させる（実行モデルは同じファイルの末尾に実行報告を追記して返す）。

## 運用ルール

- 1 タスク = 1 ファイル。**必ず対象プロジェクトの `tasks/` に置く**（発注側リポジトリに置くと、対象プロジェクトで開いた実行セッションから見つけられない。初回パイロットで実証済み）。
- 実行モデルへの発注文は「`<タスクファイルの絶対パス>` のタスクを実行して」の形で、**絶対パス**を渡す。
- ファイル名: `T-YYYYMMDD-nn_短いスラッグ.md`（例: `T-20260702-01_fix-receipt-path-traversal.md`）
- status 遷移: `ready` →（実行モデルが着手時に）`in-progress` → `done` または `returned`
- **AC（受け入れ条件）の書き方が全てを決める。** 「〜が正しく動くこと」のような検証不能な AC は禁止。必ず「実行コマンド＋期待結果」で書く。目視確認が避けられない場合は、確認手順と合格基準を具体的に書く。AC は 3〜7 個。
- 背景説明は実行に必要な最小限にする。長い経緯は KNOWLEDGE.md / ADR へのパス参照で済ませる。
- **テスト基盤のないプロジェクトでは、既存のツールチェーンを AC に流用する**（`tsc --noEmit`、`npm run build`、`python -m py_compile`、linter など）。それも無い場合のみ「目視＋具体的な合格基準」を許容し、テスト基盤の導入自体を別タスクとして検討する。
- **リポジトリ全体に効くコマンド（tsc / 全テスト等）を AC にする前に、発注者はベースラインを実測する。** ベースラインが既に赤い場合、そのままでは「スコープを守れ」と「全体 green にしろ」が矛盾し、正しく動く実行モデルほど ac-dispute で返ってくる。対処は (a) 既存の赤を先に独立タスクで修正する、または (b) AC を「変更ファイルに新規のエラー/失敗を持ち込まない（ベースライン比較）」形式にする。
- **複数タスクが同じ作業ツリーで並走する場合**、「git status がクリーン」「コミットを作る」類の AC はパス限定で書く（他タスクの未コミット変更を巻き込むため）。

## テンプレート（ここから下をコピーして使う）

```markdown
# T-YYYYMMDD-nn <タスク名>

- status: ready            <!-- ready / in-progress / done / returned -->
- issuer: fable-5
- executor: sonnet-5       <!-- 01_model-selection.md による指定 -->
- effort: low              <!-- low / medium / high -->
- project: <プロジェクトのルートパス>
- created: YYYY-MM-DD
- attempts: 0              <!-- 実行モデルが自己修正のたびに +1。上限 2 -->

## 1. ゴール
<1〜3 行。何ができれば終わりか>

## 2. 背景（最小限）
<実行に必要な文脈のみ。詳細は参照で: 例「経緯は docs/adr/0003 参照」>

## 3. スコープ
### 変更してよいファイル
- <パス>
### 触ってはいけないもの（非スコープ）
- <パス、機能、設定。「〜はやらない」も明記>

## 4. 制約
- <技術制約、依存関係、コーディング規約、使ってよい/いけないライブラリ>

## 5. 受け入れ条件（AC）
<!-- 必ず「コマンド → 期待結果」形式。これが検証ループの起点 -->
- [ ] AC-1: `<コマンド>` → <期待出力 / 終了コード 0>
- [ ] AC-2: `<コマンド>` → <期待結果>
- [ ] AC-3: <目視の場合: 手順と合格基準を具体的に>

## 6. 自己検証手順
1. 全 AC を上から順に実行する。
2. 失敗した AC があれば修正して再実行（attempts を +1）。attempts が 2 に達してなお失敗するなら中断し、status を returned にする。
3. AC 自体が誤っている・実現不能と判断した場合、AC を書き換えてはならない。status: returned、reason: ac-dispute として理由を実行報告に書く。

## 7. 完了の定義（DoD）
- 全 AC 通過
- 本ファイル末尾の実行報告を記入し status を done に更新
- <該当時: KNOWLEDGE.md の該当項目を更新>

---
## 実行報告（実行モデルが追記する）
- 結果: done / returned（reason: failed / ac-dispute / blocked）
- AC 結果: AC-1 ✅ / AC-2 ✅ / AC-3 ✅
- 変更ファイル: <一覧>
- （attempts > 0 の場合）自己修正の内容: <何に失敗し、何を直したか 1 行。done でも必須>
- 逸脱・気づき: <仕様からズレた点、次に活かすべき発見。なければ「なし」>
- 失敗ログ（returned の場合のみ）:
  - 現象: <何が起きたか。エラー出力を貼る>
  - 試行: <何を試したか（attempts ごと）>
  - 仮説: <なぜ失敗していると考えるか>
```

改訂履歴
- 1.4 (2026-07-02) 実運用反映: 全体コマンド AC の前にベースライン実測を必須化（既存の赤があると正しい実行モデルほど ac-dispute で返る — ある案件で 3 タスク同時差し戻しの実例）。並走タスクの AC はパス限定に。
- 1.3 (2026-07-02) パイロット反映: attempts > 0 で done になった場合も自己修正の内容を 1 行報告する欄を追加（中身が不明だった事例）。また実行モデルはタスクファイルの見出し構造を崩さないこと。
- 1.2 (2026-07-02) パイロット反映: タスクは対象プロジェクトの tasks/ に置くことを必須化、発注文は絶対パスで渡す旨を追記（相対パスで探して見つけられなかった事例）。
- 1.1 (2026-07-02) パイロット反映: テスト基盤のないプロジェクトでの AC 指針を追加。
- 1.0 (2026-07-02) 初版制定。
