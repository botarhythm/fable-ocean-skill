# 02 ハンドオフ文書テンプレート

version: 2.1 (2026-10-19) / 制定: Fable-5（v1）、改訂: 指令塔 Opus 5.5（v2）

指令塔が発注し、実行モデル（01 §2 で解決したモデル）の**新規セッション**が単独で消費する仕様書。往復は 1 ファイルで完結させる（実行モデルは同じファイルの末尾に実行報告を追記して返す）。

## 運用ルール

- 1 タスク = 1 ファイル。**必ず対象プロジェクトの `tasks/` に置く**（発注側リポジトリに置くと、対象プロジェクトで開いた実行セッションから見つけられない。初回パイロットで実証済み）。
- 実行モデルへの発注文は「`<タスクファイルの絶対パス>` のタスクを実行して」の形で、**絶対パス**を渡す。
- ファイル名: `T-YYYYMMDD-nn_短いスラッグ.md`（例: `T-20260702-01_fix-receipt-path-traversal.md`）
- status 遷移: `ready` →（実行モデルが着手時に）`in-progress` → `done` または `returned`。不可逆操作（01 の Q3）を含むタスクは、承認欄が埋まるまで該当する AC を実行せず `awaiting-approval` で止める。
- **ヘッダのモデル欄には、01 §2 で解決した具体的なモデルIDを書く**（役割名ではなく `claude-sonnet-5-5` のように）。あわせて適用した 01 の版を `model-rule` に書く。後で 01 が変わっても、そのタスクを当時どのモデルで回したかが読めるようにするため。
- **AC（受け入れ条件）の書き方が全てを決める。** 「〜が正しく動くこと」のような検証不能な AC は禁止。必ず「実行コマンド＋期待結果」で書く。目視確認が避けられない場合は、確認手順と合格基準を具体的に書く。AC は 3〜7 個。
- 背景説明は実行に必要な最小限にする。長い経緯は KNOWLEDGE.md / ADR へのパス参照で済ませる。
- **テスト基盤のないプロジェクトでは、既存のツールチェーンを AC に流用する**（`tsc --noEmit`、`npm run build`、`python -m py_compile`、linter など）。それも無い場合のみ「目視＋具体的な合格基準」を許容し、テスト基盤の導入自体を別タスクとして検討する。
- **リポジトリ全体に効くコマンド（tsc / 全テスト等）を AC にする前に、発注者はベースラインを実測する。** ベースラインが既に赤い場合、そのままでは「スコープを守れ」と「全体 green にしろ」が矛盾し、正しく動く実行モデルほど ac-dispute で返ってくる。対処は (a) 既存の赤を先に独立タスクで修正する、または (b) AC を「変更ファイルに新規のエラー/失敗を持ち込まない（ベースライン比較）」形式にする。
- **複数タスクが同じ作業ツリーで並走する場合**、「git status がクリーン」「コミットを作る」類の AC はパス限定で書く（他タスクの未コミット変更を巻き込むため）。

## テンプレート（ここから下をコピーして使う）

```markdown
# T-YYYYMMDD-nn <タスク名>

- status: ready            <!-- ready / in-progress / awaiting-approval / done / returned -->
- issuer: <指令塔のモデルID>        <!-- 例: claude-opus-5-5 -->
- executor: <01 §2 で解決したモデルID> <!-- 例: claude-sonnet-5-5 / deepseek-flash -->
- effort: low              <!-- low / medium / high / xhigh -->
- model-rule: 01 v2.1      <!-- 適用した 01 の版 -->
- auditor: <監査者と対象リビジョン> <!-- 監査に当たったとき記入。実装した系統と別の系統（03 §2）。例: codex @ a1b2c3d -->
- irreversible: no         <!-- yes なら §8 承認欄が必須（01 の Q3） -->
- project: <プロジェクトのルートパス>
- created: YYYY-MM-DD
- attempts: 0              <!-- 実行モデルが自己修正のたびに +1。上限 2 -->

## 1. ゴール
<1〜3 行。何ができれば終わりか>

## 2. 背景（最小限）
<実行に必要な文脈のみ。詳細は参照で: 例「経緯は docs/adr/0003 参照」>

## 3. スコープ
### 変更してよいファイル
- <パス>
### 触ってはいけないもの（非スコープ）
- <パス、機能、設定。「〜はやらない」も明記>

## 4. 制約
- <技術制約、依存関係、コーディング規約、使ってよい/いけないライブラリ>

## 5. 受け入れ条件（AC）
<!-- 必ず「コマンド → 期待結果」形式。これが検証ループの起点 -->
- [ ] AC-1: `<コマンド>` → <期待出力 / 終了コード 0>
- [ ] AC-2: `<コマンド>` → <期待結果>
- [ ] AC-3: <目視の場合: 手順と合格基準を具体的に>

## 6. 自己検証手順
1. 全 AC を上から順に実行する。
2. 失敗した AC があれば修正して再実行（attempts を +1）。attempts が 2 に達してなお失敗するなら中断し、status を returned にする。
3. AC 自体が誤っている・実現不能と判断した場合、AC を書き換えてはならない。status: returned、reason: ac-dispute として理由を実行報告に書く。

## 7. 完了の定義（DoD）
- 全 AC 通過（irreversible: yes のタスクは「実装の完了」と「本番操作の完了」を分けて書く）
- 本ファイル末尾の実行報告を記入し status を done に更新
- <該当時: KNOWLEDGE.md の該当項目を更新>

## 8. 承認欄（irreversible: yes のときだけ。指令塔とユーザーが記入する）
- 承認対象の操作: <何を・どの環境で（例: 本番 DB のマイグレーション 0012）>
- 対象リビジョン: <コミットハッシュ>
- 別系統レビュー: <ocean-review の記録のパス>
- 着手承認: <ユーザーの承認日時と方法。空欄なら該当 AC を実行しない>
- 事後確認: <実行ログ・差分の場所、別系統の確認結果、ユーザーの完了確認>

---
## 診断記録（指令塔が追記する。returned を診断するたびに1行）
<!-- 判断の失敗は実装の attempts とは別に数える。再発注・分割しても、この記録を新しいタスクへ引き継ぐ。blocked・環境不足は失敗に数えない。同じ判断で2回外したら昇格先をユーザーに提案する（01 §3） -->
- D-1: <判断（AC 修正 / 分解 / 1段上へ）> / 仮説: <なぜそう判断したか> / 結果: <当たった・外れた>

---
## 実行報告（実行モデルが追記する）
- 結果: done / returned（reason: failed / ac-dispute / blocked）/ awaiting-approval
- AC 結果: AC-1 ✅ / AC-2 ✅ / AC-3 ✅
- 変更ファイル: <一覧>
- （attempts > 0 の場合）自己修正の内容: <何に失敗し、何を直したか 1 行。done でも必須>
- 逸脱・気づき: <仕様からズレた点、次に活かすべき発見。なければ「なし」>
- 失敗ログ（returned の場合のみ）:
  - 現象: <何が起きたか。エラー出力を貼る>
  - 試行: <何を試したか（attempts ごと）>
  - 仮説: <なぜ失敗していると考えるか>
```
