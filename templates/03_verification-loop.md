# 03 検証ループの定義

version: 1.3 (2026-07-03) / 制定: Fable-5

目的: 下位モデルの成果確認を機械化し、**Fable-5 の関与を 3 点だけに絞る**ことでコストを最小化する。

## 0. 大原則

**検証の品質は AC（受け入れ条件）の品質で決まる。** 検証ループが機能しない原因の大半は「実装が悪い」ではなく「AC が甘い（検証不能・網羅不足）」。returned が続くタスクは、まず実装ではなく AC を疑うこと。

## 1. 標準フロー

```
Fable-5                     実行モデル (Opus/Sonnet)
───────                     ─────────────────────
AC 付きタスク発注 (ready)
        │
        └──────────────────▶ 着手 (in-progress)
                             実装
                             AC を上から順に実行
                              ├─ 全通過 ─▶ 実行報告を追記し done  ※Fable-5 の確認不要
                              └─ 失敗 ──▶ 自己修正して再実行（最大 2 回 = attempts ≤ 2）
                                           └─ なお失敗 ─▶ 失敗ログ付きで returned
        ┌──────────────────────────────────────────────┘
        ▼
returned の診断（下記 3 分岐）
```

## 2. Fable-5 が関与するのは 3 点だけ

1. **AC 設計時**（発注時）— ここに最も投資する。AC が機械検証可能なら以降は自走する。
2. **returned 時** — 診断して 3 分岐:
   - **AC が悪い** → AC を修正して再発注
   - **タスクが大きすぎる** → 分解して複数タスクに再発注
   - **本当に難しい** → 1 段上のモデルに再発注、または Fable-5 自身が解く
3. **抜き取り監査** — done を全件確認しない。目安:
   - 通常タスク: 5 件に 1 件程度をサンプリング
   - **全件監査に格上げする条件**（いずれか該当で 5:1 を上書き）:
     1. 不可逆操作・セキュリティ関連（01 の Q3 該当）
     2. その executor がそのプロジェクトで最初に返した done（キャリブレーション）
     3. 機械検証 AC を 1 つも含まない done（合否が目視のみで決まる = すり抜け余地が大きい）
     4. attempts > 0 の done（自己修正が入った合格は AC すり抜けの温床。実例: 実行報告の過大申告があった）
   - 監査の観点は「AC は通ったが仕様の意図を満たしていない」ケース、つまり **AC の穴を探す**。穴が見つかったら該当タスクの修正よりも先にテンプレ/AC の書き方に反映する。

## 3. 実行モデル側の義務

- AC を**改変しない**。おかしいと思ったら `returned (reason: ac-dispute)` で理由を添えて返す。
- attempts 上限（2）を守る。3 回目を粘らない — それは 1 段上のモデルの仕事。
- 実行報告の「逸脱・気づき」を必ず書く。空欄にしない（「なし」と明記はよい）。ここが型の改善材料になる。
- スコープ外のファイルに触れる必要が生じたら、勝手に触らず `returned (reason: blocked)` で返す。

## 4. 差し戻し文書の品質基準

failed で返すときの失敗ログは次の 3 点が揃っていること。揃っていない差し戻しは Fable-5 の診断コストを増やすだけになる。

- **現象**: エラー出力・失敗した AC の実際の出力を貼る（要約ではなく生の出力）
- **試行**: attempts ごとに何を変えたか
- **仮説**: なぜ失敗していると考えるか（外れていてもよい。診断の起点になる）

## 5. ハードウェア・実機依存タスクの特則（重要）

物理デバイス／実行環境の挙動に依存するタスク（組込み・ロボット・音声・タイミング・GPU 等）では、AC と監査に次を追加する。組込み音声AIの案件で、PC のユニットテストが全 green でも実機のウェイクワードが壊れた事例に基づく。

- **PC テストの green は実機の正常動作を保証しない。** 実機でしか出ない競合（CPU・オーディオデバイス・タイミング）がある。AC に「実機での受け入れ確認」を必ず含める（例: 「実機でウェイク 10 回中 9 回反応」）。実機確認が必要な部分はユーザーが担う前提で DoD に書く。
- **1 変更ずつ適用し、都度実機確認。** 複数の変更（例: 聴取改善 + 音声エンジン変更）を同時に載せると、障害の切り分けが不能になる（聴取と TTS を同時変更し診断が混線した事例）。
- **推測で実機の状態を変えない。** ログの一見の症状から即断せず、実機の実データを取ってから動く。生きているデバイスの上で仮説検証を繰り返さない。
- **実機とリポジトリの乖離を文書化する。** 実機に個別配備した結果、実機の実体とリポジトリの作業ツリーが食い違うことがある。ファイルごとの対応表（実機の実体 / 配備してよいか）を引き継ぎ文書に残す。

## 6. 発注の自動ディスパッチ（オプション）

文書ハンドオフの原則は変えずに、「タスクファイルを実行セッションに渡す」工程だけは自動化できる。Fable-5 のセッションが Agent ツール（サブエージェント、モデル指定つき）に標準の発注文＋タスクファイルの絶対パスを渡せば、人手のコピペと等価に実行される。

- 正本は変わらず対象リポジトリの `tasks/T-*.md`。実行報告も同ファイルに返るため、手動発注と監査性は同じ。
- 自動ディスパッチ時はサブエージェントに追加で伝える: 作業ディレクトリ、**並走する他タスクの未コミット変更に触れない**（git stash / checkout 禁止）、コミット可否。
- 手動発注が向くケース: ユーザーが途中の権限確認を自分で判断したい場合、長時間の対話的作業。
