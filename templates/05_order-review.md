# 05 レビュー発注テンプレート（既存プロジェクトの丸投げレビュー）

version: 1.2 (2026-07-02) / 制定: Fable-5

既存プロジェクトを Fable-5 に一括レビューさせるときの発注フォーマット。Fable-5 は**発見 → 検証（誤検出排除）→ 優先順位づけ → 修正タスク化（02 テンプレ）まで一気通貫**で行う。修正の実装は行わない（それは 01 のルールで下位モデルへ）。

## 発注書（コピーして使う）

```markdown
# レビュー発注: <プロジェクト名>
- 発注日: YYYY-MM-DD
- 対象: <ルートパス。ブランチ、対象/除外ディレクトリ>
- 目的: <なぜ今レビューするか。例: リリース前 / 引き継ぎ準備 / 劣化診断 / セキュリティ点検>

## 評価軸と重み（H/M/L で指定。L は「見なくてよい」ではなく「深掘りしない」）
- 正しさ（バグ）: H/M/L
- セキュリティ: H/M/L
- 保守性・引き継ぎ可能性: H/M/L
- パフォーマンス: H/M/L
- ※ **秘密情報スキャンは重みに関わらず必ず実施**（.env 以外の平文認証情報・鍵・トークンを、コードだけでなく **md/yaml 等の文書ファイル含めて** grep する。実績: あるレビューで仕様書 md 内のホスティングパスワードを検出。3 並列の一次調査は全員見逃した）

## 深度
- quick    : 構造把握 + ホットスポットのみ（対象が初見/巨大なときの一次診断）
- standard : 主要フローの精読（既定値）
- deep     : 全ファイル精読 + 実際にビルド/テストを実行して検証

## 前提知識
- <既知の問題（重複指摘を避ける）>
- <触ってはいけない領域・設計上わざとそうなっている箇所>
- <動作環境の前提（例: 家庭内 LAN のみ、認証は VPN 層で担保、など）>

## 成果物
- REVIEW_REPORT.md（下記書式）
- 上位 <N> 件の修正タスク化（02 テンプレ、実行モデル指定込み）
```

## REVIEW_REPORT.md の書式

```markdown
# レビュー報告: <プロジェクト名> (YYYY-MM-DD)

## サマリ（3〜5 行）
<全体評価。今すぐ直すべきものは何件か。放置してよいものは何か>

## 所見一覧
| ID | 重大度 | 場所 | 問題（1行） | 修正規模 |
|----|--------|------|------------|---------|
P0: 悪用可能・データ破壊しうる。即修正
P1: 高。今回の対応範囲に含めるべき
P2: 中。次の機会に
P3: 低。記録のみ

各所見の詳細（根拠のコード引用付き。引用できない所見は載せない）

## 優先順位と対応計画
<どれをタスク化するか、その順序と理由。どのモデルに振るか（01 適用）>

## タスク化しなかった所見の扱い
<P2/P3 を KNOWLEDGE.md の「既知の問題」に転記した旨>
```

## 運用手順（Fable-5 側）

1. 発注書を受領し、評価軸に応じて観点別の並列調査を行う（観点ごとに独立したエージェント/パスで見る。1 パスに全観点を混ぜない）。
2. 所見は**根拠のコード引用があるものだけ**採用する。伝聞・推測の所見は捨てる。
3. **一次調査の重大度判定を信用しない。** 発注者（Fable-5）が根拠を実コードで再確認し、重大度を再判定してから報告に載せる。実績: 初回パイロットでは一次の P0 判定 3 件がすべて過大評価で、うち誤検出も 4 件あった（JS `Date` の月あふれ・`??` 演算子の挙動など、もっともらしい根拠つきの誤りが混ざる）。
4. 重大度は「動作環境の前提」を織り込んで判定する（例: 認証なし API は、公開環境なら P0、プライベートネットワーク内限定なら P2）。
5. 上位 N 件を 02 テンプレでタスク化。残りは KNOWLEDGE.md の「既知の問題」へ転記して発注完了。
