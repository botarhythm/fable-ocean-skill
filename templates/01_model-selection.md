# 01 モデル選択ルール

version: 2.1 (2026-10-19) / 制定: Fable-5（v1）、改訂: 指令塔 Opus 5.5（v2、ocean-review 交差レビュー済み）

**モデル名・世代はこのファイルにだけ書く。** ほかのテンプレートは「指令塔」「実行モデル」「昇格先」「外部の器」という役割名で書き、具体的なモデルはこのファイルの §2 で解決する。実際のタスクファイルには、解決したモデルID・effort・このファイルの版を記録する（02 のヘッダ）。

## 0. たたき台の批判と設計方針

当初案は「設計・レビュー = 最上位モデル、単純実装 = 中位、中間 = その間」だった。この**タスク種別による分類は捨てる**。同じ「実装」でも本番 DB マイグレーションと CSS 修正では必要な知性が違い、同じ「設計」でも前例のコピーで済む設計なら安いモデルで足りる。種別ではなく、次の 3 軸で決める。

1. **曖昧さ** — 仕様の解釈余地・判断の分岐数。ゴールを機械検証可能な受け入れ条件（AC）に書き切れるか。
2. **誤りの検出コスト** — 間違いを AC で自動検出できるか、それとも後から人間が気づくしかないか。
3. **影響半径** — 失敗したときの波及範囲。不可逆か（本番データ・公開・課金・削除）。

## 1. 判定手順（3 問で決める）

- **Q1. このタスクの AC を「コマンド＋期待結果」で書き切れるか？**
  - 書き切れない（判断そのものが成果物）→ **指令塔**（effort `xhigh`）
  - 書き切れる → Q2 へ
- **Q2. 失敗は AC で自動検出でき、影響は対象ファイル内に閉じるか？**
  - はい → **軽い実行モデル**、または**外部の器**（§2）
  - 道中に自律判断が残る（複数ファイル横断、既存設計への適合判断、仕様の小さな穴埋め）→ **判断の残る実行モデル**（§2）
- **Q3. 不可逆操作（本番データ変更・マイグレーション・公開・課金・削除）を含むか？**
  - 含む → 実行モデルは Q1/Q2 の結果のままでよい。ただし手順は §3 の2段停止に固定し、実行そのものは外部の器に出さない（Claude 側かユーザーが実行する）。

## 3. エスカレーションとデエスカレーション

- **2 敗ルール（実行モデルの昇格）**: 実行モデルが同一タスクで自己修正 2 回に失敗したら（02 の `attempts`）、それ以上粘らせず 1 段上へ差し戻す。軽い実行モデル → 判断の残る実行モデル → 指令塔の直営、の順。失敗ログ（02 の実行報告）を必ず添える。3 回目の試行を同じモデルでやらせるのが一番高くつく。
- **判断の2敗（昇格先への昇格）**: 指令塔の判断（returned 診断・設計・裁定）が外れた回数は、実装の `attempts` とは別に、02 の「診断記録」で数える。再発注・分割をしても記録は引き継ぐ。**同じ判断で2回外したら**、昇格先への投入をユーザーに提案する（従量課金なので承認ゲートを通す）。`blocked` や実行環境の不足は、判断の失敗に数えない。
- **型化ルール（降格）**: 一度解いてパターン化した仕事は、2 回目以降は軽い実行モデルか外部の器へ降ろす。「1 回目は上で解いて手順書にし、N 回目は下で回す」が基本形。
- **迷ったら 1 段安い方**に出す。エスカレーション経路が失敗を回収するので下振れの損は小さい。逆（高いモデルに安い仕事）は回収できない。
- **判断を伴う仕事では、モデルを下げる前に effort を下げる**: Q1 と Q2 の「道中に判断が残る」仕事では、別のモデルへ切り替える前に、同じモデルの effort を1段下げて試す。最上位に近いモデルの低い effort が、下位モデルの高い effort と同等以上になることが多く、キャッシュはモデル単位なので切替は再読込を増やす。Q2 で AC が閉じる定型は、従来どおり軽い実行モデルか外部の器に出す（判断の残るモデルの thinking は無効にできず、定型には割高）。監査・診断・Q3 の effort（`xhigh`）は、この規則で下げない。
- **Q3 の2段停止**: 計画（指令塔 `xhigh`）→ 別系統レビュー（ocean-review）→ **停止: 対象操作に対するユーザーの着手承認** → 実行 → 一次情報（ログ・差分）を生で取得して別系統で確認 → **停止: ユーザーの完了確認**。承認の記録は 02 の承認欄に残す。

## 4. effort レベル（モデルと直交する第 2 のレバー）

| 役割 | 推奨 effort | 起動コマンド例 |
|---|---|---|
| 指令塔（通常） | high | `claude --model claude-opus-5-5 --effort high` |
| 指令塔（AC 設計・監査・診断・裁定・Q3 計画） | xhigh | `claude --model claude-opus-5-5 --effort xhigh`（セッション中は `/effort xhigh`） |
| 判断の残る実行モデル | medium（難タスクのみ high） | `claude --model claude-opus-5-5 --effort medium` |
| 軽い実行モデル | low | `claude --model claude-sonnet-5-5 --effort low` |
| 昇格先 | xhigh | `claude --model claude-fable-5-1 --effort xhigh` |

運用の仕組み（モデルの事実は Anthropic 公式のモデル表 2026-10-06 時点）:
- **Opus 5.5 の effort の既定は `medium`**（Opus 5 の `high` より1段低い）。thinking は無効にできず、effort が唯一の調整手段。指令塔は起動時に `high` か `xhigh` を明示する。
- グローバル設定は `medium` を床にする。設計・レビュー専用のリポジトリはプロジェクト設定で `xhigh` にしてよい（設定スコープはプロジェクト > ユーザーの優先で自動適用）。
- ハンドオフ文書の `effort:` フィールドが個別タスクの指定値。発注時の起動コマンドに反映する。セッション中の変更は `/effort <level>`。
- **下げ忘れは静かにコストになるが、上げ忘れは品質低下として気づける** — だから床は低めに置き、明示的に上げる。

## 5. コスト原則

- **判断の出力は「再利用される文書」に落とす。** 1 回の思考を仕様書・規約・ADR として N 回使う。指令塔の単価は下がったが、チャットで消える回答に判断を浪費しない原則は変わらない。
- コンテキストもコスト。実行モデルのセッションには必要最小限の文書だけ読ませる（04 のコールドスタート規約参照）。
- **従量課金が発生する投入**（昇格先・DeepSeek・サブスク枠の超過）は、金額の大小に関係なく、承認済みの用途と上限の範囲内かを確かめてから行う（`skills/ocean` §7）。
