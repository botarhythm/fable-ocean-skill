# 06 フルスタック発注テンプレート（新規開発の一気通貫）

version: 1.1 (2026-10-19) / 制定: Fable-5（v1.0）、改訂: 指令塔 Opus 5.5（v1.1）

新規に何かを作るとき、指令塔が要件定義 → 設計 → タスク分解 → 検証計画まで担い、実装は実行モデルに流す発注フォーマット。**要件・設計についてのユーザーの確認ゲートは 2 回**（要件確定時・設計確定時）。以降は検証ループ（03）で自走する。**ただし不可逆操作（本番データ・公開・課金・削除）の承認は、この 2 回とは別に、操作ごとに必ず取る**（01 §3 の2段停止、02 の承認欄）。

## 発注書（コピーして使う）

```markdown
# 開発発注: <プロジェクト名>
- 発注日: YYYY-MM-DD
- 置き場所: <リポジトリを作るパス>

## 目的（1〜3 行）
<誰の何の問題を解決するか。ビジネス上のゴール>

## コア機能（3 つまで。4 つ目以降は「あれば嬉しい」欄へ）
1. <機能>
2. <機能>
3. <機能>

## あれば嬉しい（初期リリースには入れない前提）
- <機能>

## 対象ユーザーと利用環境
<誰が、どの端末/環境で使うか。同時利用者数の目安>

## 制約
- 技術: <指定スタック / 避けたい技術 / 既存資産との連携>
- 予算: <外部サービス課金の上限、モデル利用コストの意識>
- 期限: <いつまでに何が動けばよいか>

## 非機能要件（該当するものだけ）
- 認証の要否 / データの機微性 / バックアップ / オフライン動作 / 多言語

## やらないこと
<スコープ外を明文化。ここが曖昧だと膨張する>
```

## 指令塔の出力物（この順で作る）

| # | 成果物 | 内容 | ゲート |
|---|---|---|---|
| 1 | `docs/requirements.md` | 要件定義: コア機能の受け入れ条件レベルまでの具体化、画面/API の一覧 | ★ ユーザー確認 1 |
| 2 | `docs/adr/0001〜` + 構成図 | 技術選定と構造。重要なトレードオフは ADR 化 | ★ ユーザー確認 2 |
| 3 | リポジトリ雛形 | `CLAUDE.md` / `KNOWLEDGE.md` / `tasks/` / `docs/adr/`（04 の規約を適用） | — |
| 4 | `tasks/T-*.md` 一式 | 実装タスクへの分解（02 テンプレ）。依存順に番号付け、各タスクに実行モデル指定（01 適用） | — |
| 5 | 統合 AC | 全タスク完了後にプロダクト全体として通すべき受け入れ条件（E2E 相当） | — |

## 進行ルール

- タスクは依存順に発注する。並行可能なタスクは明記する（別セッションで同時進行できる）。
- 実装中の設計変更が必要になったら、実行モデルは自分で設計変更せず `returned (reason: blocked)` で返す。指令塔が ADR を追記してからタスクを修正する。
- 完了判定: 全タスク done + 統合 AC 通過 + 最終監査 1 回（03 の抜き取り監査を全体に 1 回だけ適用。監査者は実装と別の系統、指令塔が裁定）。不可逆操作を含む場合は、ユーザーの完了確認まで終えて完了とする。
